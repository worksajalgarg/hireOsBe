# 0006 — Interview transcript/evaluation storage, and the one deliberate outbound exception to "ai-service never calls back into platform"

## Status
Accepted

## Context
Before this ADR, a completed interview's transcript and any post-call evaluation existed only in `ai-service`'s dev-only, ephemeral `.dev/*.jsonl` files (gitignored, gated behind `DEV_METRICS_ENABLED`, one developer's local machine). In production this is real data loss: the moment a worker process exits, the exact evidence `CLAUDE.md` says this product exists to produce is gone.

A prior, larger plan (config/prompt/voice management via a DB-backed admin surface, and a multi-stage interview redesign) was reviewed and explicitly deferred as scope creep ahead of validated need — see the CTO-review section of the working plan this ADR's implementation came from. This ADR covers only the part of that plan judged actually production-blocking: durable transcript + evaluation storage.

## Decision
1. **Storage lives in `platform`'s existing Postgres**, not a new `ai-service` DB connection — `InterviewTranscript`/`InterviewSummary` models, one row each per `InterviewSession`, tenant-scoped like every other table in that schema.
2. **`ai-service` pushes, once, after the call ends** — a `ctx.add_shutdown_callback()` in `voice_agent/worker.py`'s `entrypoint()` builds the full transcript (`llm_streaming.extract_structured_transcript()`), runs one structured evaluation call through `model_gateway`'s existing `interview_evaluation` use case (`post_call_evaluation.py` — never a direct provider call, same boundary every other use case respects), and POSTs both to a new `platform` endpoint.
3. **This is the one deliberate, scoped exception to `worker.py`'s "never calls back into platform" design.** It is safe specifically because it's outbound, post-call, and best-effort: the interview itself never depends on `platform` responding. A `platform` outage delays persistence, never the call. (A separate, since-deferred proposal — fetching routing/prompt config from `platform` *before* dispatch — was rejected specifically because that direction of coupling *would* make interview dispatch depend on `platform`'s uptime; this ADR does not reopen that decision.)
4. **Delivery reliability via a local outbox, not a message queue.** `transcript_delivery.py` writes the payload to `ai-service/data/pending_transcripts/<sessionId>.json` before attempting the POST, deleting it only on a confirmed 2xx. `flush_pending()` retries anything still there at the next worker startup. If volume ever justifies it, `platform` already has ElasticMQ/SQS-style infra to move this onto — not needed at pilot scale.
5. **Service-to-service auth is one shared secret, not per-feature.** `INTERNAL_SERVICE_SECRET` (identical value in both services' `.env`), checked by a new `InternalServiceGuard` (timing-safe comparison) scoped to `platform`'s `/internal/*` routes. Any future internal call reuses this secret/guard rather than minting a new one.
6. **`evaluationJson` is a scoped-down shape (`InterviewEvaluationSummary`), not the full `CandidateEvaluation` type.** `CandidateEvaluation` (in `platform/src/common/types/evaluation.ts`) requires `roleId`/`rubricVersion` — no rubric or role-context system exists yet (both are later-sprint work per `CLAUDE.md`), so those fields have nothing real to reference. `InterviewEvaluationSummary` reuses the same `recommendation`/`EvidenceStrength` values, so it's forward-compatible: once a rubric system exists, add the two missing fields rather than replacing the shape. It never contains a bare score — evaluation LLM failures degrade to an `"insufficient_data"` recommendation with a clear reason, never silently to a worse signal about the candidate (per `CLAUDE.md`'s Responsible AI constraint that a technical failure must never read as a negative signal).
7. **`candidateRef` is authoritative from `platform`, not `ai-service`.** Room metadata never carried it, and `ai-service` has no reliable way to know it; `platform`'s `ingestTranscriptAndSummary` always overwrites whatever `ai-service` sent with the real `InterviewSession.candidateRef`.
8. **Retention is wired into the existing `TenantPolicy.retentionDays`**, not a new, unmanaged retention surface — a daily `@Cron` job (`InterviewRetentionService`) deletes transcript/summary rows past each tenant's own window.

## Consequences
- A `platform` outage no longer risks losing interview data (outbox + retry), but does mean transcripts/evaluations lag until it recovers — acceptable, since nothing candidate-facing depends on it.
- The evaluation LLM call adds real latency to worker shutdown; `AgentServer(shutdown_process_timeout=60.0)` was raised from the framework's 10s default to give it room.
- `INTERNAL_SERVICE_SECRET` is a new operational secret that must be provisioned identically in both services for every environment — a deployment checklist item, not just a `.env.example` line.
- This does not build: an admin UI, DB-backed prompt/model/voice config, or the multi-stage interview redesign — all explicitly deferred pending real evidence of need (see the CTO-review section of the source plan).
